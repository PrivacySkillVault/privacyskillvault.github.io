# MFA, OTPs and Passkeys: What Actually Makes Authentication Stronger?

<small>SECURITY EXPLAINERS · IDENTITY & ACCESS · 01 NOV 2026</small>

<p class="psv-article-breadcrumb"><a href="../">← Security Explainers</a><span> / </span><a href="../../">Cyber Journal</a></p>

Authentication is the process of establishing that a person or system controls an authenticator associated with an identity. Multi-factor authentication (MFA) strengthens this process by requiring evidence from more than one factor category. But not every second step offers the same resistance to phishing or account takeover.

## 1. What counts as a factor?

Common factor categories include:

- **Something you know:** a password or PIN.
- **Something you have:** a hardware security key or registered authenticator.
- **Something you are:** a biometric characteristic used by an authenticator.

Two passwords are still one factor category. A password plus a separate possession-based authenticator is a multi-factor combination.

## 2. One-time passwords

An OTP may be generated by an authenticator application, sent through a messaging channel, or delivered through another mechanism. OTPs can improve security compared with a password alone, but they are not all equally resistant to phishing.

A real-time phishing site can relay a user-entered OTP to the genuine service before the code expires. SMS delivery also depends on the security of the phone number and telecom account. OTPs should not be described as universally phishing-proof.

## 3. Push approvals

Push-based MFA can be convenient, but users may approve a request they did not initiate. Repeated prompts can create MFA fatigue. Number matching and clear transaction context can reduce some risks, but approval prompts still require user awareness and robust risk controls.

## 4. Passkeys and public-key cryptography

Passkeys use public-key cryptography. During registration, the authenticator creates a key pair. The service stores the public key; the private key remains protected by the authenticator or passkey provider.

Passkeys are bound to the relying party's identity, which makes them resistant to common credential-phishing sites. The browser and platform help ensure that the authenticator is used with the intended site or application.

This is a meaningful security improvement over passwords and manually entered OTPs, but implementation and account recovery still matter.

## 5. Recovery is part of authentication security

A strong login can be undermined by a weak recovery process. Attackers may target email accounts, phone-number changes, help-desk workflows, backup codes, or device replacement.

Review the full authenticator lifecycle:

- Registration and binding.
- Normal authentication.
- Lost-device recovery.
- Factor replacement and revocation.
- Account recovery and customer support.
- Notification and audit events.

A secure system should protect both login and recovery.

## 6. What should a defender monitor?

Monitor new authenticator registration, factor removal, recovery attempts, repeated push requests, password resets, unusual session creation, and sensitive actions after an authentication change.

For banking and other high-impact services, authentication should be complemented by transaction-level risk assessment and appropriate authorisation checks. A successful login is not blanket approval for every later action.

## Comparison

| Method | Strength | Important limitation |
|---|---|---|
| Password only | Familiar and widely supported | Reuse, phishing and credential theft |
| Password + SMS OTP | Adds a second step | SIM/number takeover and real-time phishing risks |
| Password + authenticator OTP | Adds possession-based code | Codes can be relayed by phishing |
| Push MFA | Convenient approval workflow | Fatigue and accidental approval |
| Passkey / FIDO authentication | Relying-party bound, phishing-resistant | Recovery, device security and implementation still matter |

## Key takeaways

MFA is not a single technology. OTPs, push approvals, and passkeys have different threat models. Prefer phishing-resistant authentication where supported, protect recovery and device enrolment, and keep authorisation controls separate from login.
